# 自动服务检测与故障切换

默认开启，无需定时手动操作。后台“连接服务”的 Telegram / WhatsApp 卡片提供独立开关、立即检测、最近结果、下次检测、候选进度、冷却状态及最近 40 条运行事件。设置和最近切换记录保存在 NAS 数据目录，重启后保留开关与冷却。

## 实际规则

- 每轮检测完成后等待 60 秒，分别检测 Telegram 和 WhatsApp 当前节点。页面每 5 秒读取状态，不触发检测。
- Telegram 验证 DC2 的 MTProto resPQ 响应与随机 nonce；WhatsApp 同时验证聊天 Noise ServerHello 和媒体 TLS 证书。
- 连续失败 3 次才寻找备用节点。每轮最多尝试 6 个节点，下轮继续寻找；曾验证可用的节点优先。没有通过的备用节点则保留原出口。
- 备用节点必须连续通过两次完整检测才切换。切换后冷却 600 秒，仍继续检测，但不会反复换线。
- 正常节点保持不动。若服务原来跟随通用自动选择，检测通过后固定到当前可用的实际节点，以降低出口 IP 变化。
- 候选测试通过独立、需要认证的 Docker 内部 SOCKS 通道进行。未映射主机端口，不改变当前服务出口。检测成功后只切换对应服务；只关闭该服务仍在使用旧节点的连接，让客户端重连。
- 检测期间手动切换、关闭开关或另一个控制端改变正式出口，会取消过期的自动切换。全局/直连模式下暂停，因为此时服务专用组不参与分流。
- 检测通道、本机转发或维护服务异常时暂停操作，不把基础设施故障当成节点故障。维护升级期间暂缓检测。

这些检测验证协议连通性，不登录个人账号、不发送消息，也不承诺账号登录、所有数据中心、文件上传或 WhatsApp 通话可用。

## 和通用每小时测速的区别

通用的“自动选择”组按 YAML 中的实际周期、探测地址、超时、预期状态码和容差执行 HTTP 测速；选择它的普通代理流量才能跟随低延迟节点。服务检测优先保持可用性，不按最低延迟频繁换节点。

“代理节点”页面显示实际配置及最新节点测速记录。Mihomo 当前没有提供精确的下次运行时间与逐节点完成百分比，页面不会伪造这些数据。订阅更新、配置重载、手动测速和故障检查也可能产生新的测速记录。

后台每小时检查 GitHub 更新是另一项任务；只有 main 新提交通过安全检查才会部署。部署可能导致短暂重连。

## 实现与排障

- service_watchdog.py 由后台进程自动启动，不另装代理软件或增加宿主机常驻服务。
- 隐藏策略组 / 内部监听器名称为 __kindle_service_probe，内部端口为 17893，使用从控制密钥派生的独立认证密码；不在页面输出密码。
- 状态为 data/maintenance/service-health.json，开关为 data/maintenance/service-policy.json，均通过已有的目录描述符安全存储写入。
- 手动选择固定线路时，关闭该服务的“自动检测与故障切换”可暂停自动管理。重新开启后恢复自动检查。
